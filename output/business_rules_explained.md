# LoadProductDetail 決策邏輯

**來源**: `ProductForm.frm` / `LoadProductDetail`

## 業務規則說明
此業務規則的目的是在從資料庫中載入產品詳細資訊時，檢查是否有可用的產品資料。如果資料集（rs）不是結束（EOF），則將當前產品的ID設置為資料集中對應的產品ID，並進一步載入產品的名稱、價格、庫存數量及其是否啟用的狀態。這些資訊將用於顯示在用戶界面上，讓使用者能夠查看和編輯產品的詳細資料。

## 決策邏輯
1. 檢查資料集是否到達結尾（EOF）。
   - 如果資料集未到達結尾（Not rs.EOF），則執行以下操作：
     - 將當前產品ID設置為資料集中對應的產品ID（m_CurrentProductID = CLng(rs("ProductID"))）。
     - 將產品名稱設置為資料集中對應的產品名稱（txtProductName.Text = CStr(rs("ProductName"))）。
     - 將產品價格設置為資料集中對應的單位價格（txtPrice.Text = CStr(rs("UnitPrice"))）。
     - 將庫存數量設置為資料集中對應的庫存數量（txtStock.Text = CStr(rs("StockQuantity"))）。
     - 根據資料集中對應的啟用狀態設置是否啟用的勾選框（chkActive.Value = IIf(CBool(rs("IsActive")), 1, 0)）。
     - 在分類下拉選單中選擇對應的分類（cboCategory.ListIndex = i）。

## 邊界條件與風險
1. **資料集為空**：如果資料集為空（EOF），則不會執行任何操作，可能導致用戶界面顯示不正確或無法顯示產品資訊。
2. **資料類型轉換失敗**：在將資料集中的值轉換為長整數（CLng）或字串（CStr）時，若資料格式不正確，可能會引發錯誤。
3. **分類下拉選單無對應項目**：如果資料集中提供的分類ID在下拉選單中找不到對應項目，則可能會導致分類選擇失敗。
4. **多線程問題**：如果在多線程環境下同時訪問資料集，可能會導致資料不一致或錯誤。

## 建議測試案例
1. 測試資料集為空的情況，確保不會發生錯誤且用戶界面不顯示任何產品資訊。
2. 測試資料集包含有效的產品資料，確保所有欄位（ID、名稱、價格、庫存、啟用狀態）正確顯示在用戶界面上。
3. 測試資料集中的產品ID、名稱、價格、庫存數量及啟用狀態的資料類型正確性，確保轉換不會引發錯誤。
4. 測試資料集中提供的分類ID在下拉選單中存在的情況，確保正確選擇對應的分類。
5. 測試資料集中提供的分類ID在下拉選單中不存在的情況，確保不會發生錯誤且不會選擇任何分類。

# 計算: ListIndex

**來源**: `ProductForm.frm` / `ClearForm`

## 業務規則說明
這個業務規則的目的是在清除產品表單的時候，將 `ListIndex` 的值設置為 -1。這通常表示在一個列表中沒有選擇任何項目，可能用於初始化或重置狀態，以確保在後續操作中不會誤用之前的選擇。

## 決策邏輯
- 當執行 `ClearForm` 方法時：
  - 將 `ListIndex` 設定為 -1。

## 邊界條件與風險
- 如果 `ListIndex` 的初始值不為 -1，可能會導致後續操作錯誤地引用到一個無效的列表項目。
- 在某些情況下，若未正確清除表單，可能會導致用戶界面顯示不一致或引發錯誤。
- 需要確保在使用 `ListIndex` 之前，已經檢查其值是否有效。

## 建議測試案例
1. 測試在清除表單後，`ListIndex` 是否正確設置為 -1。
2. 測試在清除表單之前，`ListIndex` 的值是否為有效的列表索引，並確認清除後的行為。
3. 測試在清除表單後，對於依賴 `ListIndex` 的其他功能是否能正常運行，確保不會因為 `ListIndex` 為 -1 而引發錯誤。

# CheckStock 決策邏輯

**來源**: `ProductForm.frm` / `CheckStock`

## 業務規則說明
這個業務規則的目的是檢查庫存是否足夠以滿足所需的數量。當資料庫查詢結果不為空時，系統將比較庫存數量與所需數量，並根據比較結果返回是否有足夠的庫存。如果查詢結果為空，則表示沒有可用的庫存，系統將返回不滿足庫存的狀態。

## 決策邏輯
- 如果查詢結果集（rs）不為結尾（Not rs.EOF）：
  - 檢查庫存（CheckStock）將等於庫存數量（StockQuantity）是否大於或等於所需數量（RequiredQty）。
- 如果查詢結果集為結尾（其他情況）：
  - 檢查庫存（CheckStock）將為假（False）。

## 邊界條件與風險
- 當庫存數量（StockQuantity）為負數時，可能會導致不正確的庫存檢查結果。
- 如果所需數量（RequiredQty）為負數或零，則可能會導致不符合業務邏輯的結果。
- 當查詢結果集（rs）為空時，系統必須確保不會發生錯誤，並正確返回假（False）。
- 需要考慮資料庫查詢的延遲或錯誤，這可能會影響庫存檢查的準確性。

## 建議測試案例
1. 測試庫存數量（StockQuantity）大於所需數量（RequiredQty）的情況，應返回真（True）。
2. 測試庫存數量（StockQuantity）等於所需數量（RequiredQty）的情況，應返回真（True）。
3. 測試庫存數量（StockQuantity）小於所需數量（RequiredQty）的情況，應返回假（False）。
4. 測試庫存數量（StockQuantity）為零的情況，應返回假（False）。
5. 測試庫存數量（StockQuantity）為負數的情況，應返回假（False）。
6. 測試查詢結果集為空的情況，應返回假（False）。
7. 測試所需數量（RequiredQty）為負數的情況，應返回假（False）。
8. 測試所需數量（RequiredQty）為零的情況，應返回真（True）如果庫存數量（StockQuantity）為零或正數。

# UpdateStock 決策邏輯

**來源**: `ProductForm.frm` / `UpdateStock`

## 業務規則說明
這個業務規則的目的是在更新產品庫存時，確保庫存數量不會低於零。當使用者嘗試將庫存數量設定為負數時，系統會檢查該產品的現有庫存是否足夠以支持這個減少。如果庫存不足，則會引發錯誤，提示使用者庫存不足的問題。

## 決策邏輯
1. 當 `Quantity` 小於 0 時：
   - 檢查該產品的庫存是否足夠以支持減少的數量（使用 `CheckStock(ProductID, Abs(Quantity))` 函數）。
   - 如果庫存不足（即 `CheckStock` 返回 `False`），則引發錯誤，提示「庫存不足」。

## 邊界條件與風險
1. **負數庫存的情況**：如果使用者不小心輸入負數，系統應能正確處理並引發錯誤。
2. **CheckStock 函數的可靠性**：如果 `CheckStock` 函數出現錯誤或無法正確返回庫存狀態，可能會導致錯誤的庫存更新。
3. **產品ID的有效性**：如果提供的 `ProductID` 無效或不存在，可能會導致 `CheckStock` 函數無法正常工作。
4. **並發操作**：在高並發情況下，庫存可能在檢查和更新之間發生變化，需考慮庫存的即時性問題。

## 建議測試案例
1. 測試情況：`Quantity` 為負數且庫存足夠，應該不會引發錯誤。
2. 測試情況：`Quantity` 為負數且庫存不足，應該引發「庫存不足」的錯誤。
3. 測試情況：`Quantity` 為 0，應該不會引發錯誤且正常執行。
4. 測試情況：`Quantity` 為正數，應該不會進入庫存檢查邏輯。
5. 測試情況：使用無效的 `ProductID`，應該能夠處理並引發相應的錯誤。
6. 測試情況：在高並發環境下進行庫存更新，檢查是否能正確處理庫存狀態。

# 計算: sql

**來源**: `ProductForm.frm` / `UpdateStock`

## 業務規則說明
這個業務規則的目的是更新產品庫存數量。當有新的庫存數量（Quantity）進來時，系統會將現有的庫存數量（StockQuantity）增加這個新的數量。這樣可以確保庫存數據的準確性和即時性，從而支持後續的銷售和庫存管理。

## 決策邏輯
1. 當有新的庫存數量（Quantity）需要更新時，觸發此規則。
2. 執行 SQL 更新語句，將 Products 表中的 StockQuantity 欄位的值更新為現有的 StockQuantity 加上新的 Quantity。
3. 確保更新操作成功執行，並反映在資料庫中。

## 邊界條件與風險
1. **庫存數量為負數**：如果 Quantity 是負數，可能會導致庫存數量變為負值，這在實際業務中是不合理的。
2. **資料庫連接問題**：在執行更新操作時，如果資料庫連接失敗，將無法更新庫存，可能導致數據不一致。
3. **Concurrency（併發）問題**：如果多個操作同時更新同一產品的庫存，可能會導致最終庫存數量不正確。
4. **資料完整性**：需要確保 Products 表中存在對應的產品記錄，否則更新將失敗。

## 建議測試案例
1. 測試正常情況：提供一個正數的 Quantity，確認庫存數量正確更新。
2. 測試負數情況：提供一個負數的 Quantity，確認系統能正確處理並拒絕更新。
3. 測試零情況：提供 Quantity 為零，確認庫存數量不變。
4. 測試資料庫連接失敗：模擬資料庫連接問題，確認系統能夠正確處理錯誤並給出相應提示。
5. 測試併發更新：模擬多個請求同時更新同一產品的庫存，確認最終庫存數量的正確性。

# 驗證: 數值範圍檢查

**來源**: `ProductForm.frm` / `UpdateStock`

## 業務規則說明
此業務規則的目的是檢查產品庫存數量（Quantity）是否為負值。若數量小於零，則表示庫存數量不合理，必須進行驗證以避免錯誤的庫存更新。

## 決策邏輯
- 若庫存數量（Quantity）小於 0，則觸發驗證失敗，顯示錯誤訊息或阻止進一步的操作。

## 邊界條件與風險
- 當庫存數量為 0 時，系統應該允許此情況，因為這表示產品目前無庫存。
- 若系統未妥善處理負數情況，可能會導致庫存數據不一致或錯誤的庫存報告。
- 需要考慮使用者輸入的方式，避免因為錯誤的輸入格式（如字母或特殊符號）導致的驗證失敗。

## 建議測試案例
1. 測試庫存數量為負值（例如 -1），應該觸發驗證失敗。
2. 測試庫存數量為 0，應該通過驗證。
3. 測試庫存數量為正值（例如 10），應該通過驗證。
4. 測試庫存數量為非數字輸入（例如 "abc" 或 "$%&"），應該觸發驗證失敗。
