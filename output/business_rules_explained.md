# LoadProductDetail 決策邏輯

**來源**: `ProductForm.frm` / `LoadProductDetail`

## 業務規則說明
這個業務規則的目的是在從資料庫中載入產品詳細資訊時，檢查是否有可用的產品資料。如果資料集（rs）不為空（即未到達結尾），則將當前產品的ID設置為資料集中對應的產品ID，並進一步載入其他產品屬性（如產品名稱、價格、庫存數量和是否啟用等）到相應的介面元素中。

## 決策邏輯
1. 檢查資料集（rs）是否到達結尾（EOF）。
   - 如果沒有到達結尾（Not rs.EOF）：
     - 將當前產品ID（m_CurrentProductID）設置為資料集中對應的產品ID（CLng(rs("ProductID")））。
     - 將產品名稱（txtProductName.Text）設置為資料集中對應的產品名稱（CStr(rs("ProductName")））。
     - 將產品價格（txtPrice.Text）設置為資料集中對應的單位價格（CStr(rs("UnitPrice")））。
     - 將庫存數量（txtStock.Text）設置為資料集中對應的庫存數量（CStr(rs("StockQuantity")））。
     - 將產品的啟用狀態（chkActive.Value）設置為資料集中對應的啟用狀態（IIf(CBool(rs("IsActive")), 1, 0)）。
     - 設定產品的分類，通過遍歷下拉選單（cboCategory）來匹配產品的分類ID。

## 邊界條件與風險
1. **資料集為空**：如果資料集為空，則不會執行任何操作，可能導致使用者界面不顯示任何產品資訊。
2. **資料類型不匹配**：如果資料集中某些欄位的資料類型與預期不符（例如，ProductID不是數字），則在轉換時可能會引發錯誤。
3. **下拉選單無匹配項目**：如果資料集中的分類ID在下拉選單中找不到匹配項目，則可能無法正確設置分類。
4. **資料庫連接問題**：如果資料庫連接失敗，則無法載入任何產品資料。

## 建議測試案例
1. 測試資料集為空的情況，確認界面不顯示任何產品資訊。
2. 測試資料集中包含有效的產品資料，確認所有欄位正確顯示在界面上。
3. 測試資料集中包含無效的資料類型（例如，ProductID為字串），確認系統是否能正確處理錯誤。
4. 測試資料集中包含的分類ID在下拉選單中不存在的情況，確認系統的行為是否符合預期。
5. 測試資料庫連接失敗的情況，確認系統能夠妥善處理並顯示錯誤訊息。

# CheckStock 決策邏輯

**來源**: `ProductForm.frm` / `CheckStock`

## 業務規則說明
這個業務規則的目的是檢查庫存是否足夠以滿足所需的數量。當查詢結果集不為空時，系統會比較庫存數量與所需數量，並根據比較結果決定是否有足夠的庫存。如果查詢結果集為空，則表示沒有可用的庫存，系統將返回庫存不足的結果。

## 決策邏輯
- **條件**: 查詢結果集不為空 (`Not rs.EOF`)
  - **結果**: 
    - 檢查庫存數量 (`CInt(rs("StockQuantity"))`) 是否大於或等於所需數量 (`RequiredQty`)
    - 如果是，則 `CheckStock` 為 `True`，表示庫存足夠。
    - 如果否，則 `CheckStock` 為 `False`，表示庫存不足。
- **其他情況**: 
  - **結果**: `CheckStock` 為 `False`，表示沒有庫存可用。

## 邊界條件與風險
- **邊界條件**:
  - 當 `StockQuantity` 的值為負數或非整數時，可能導致比較結果不正確。
  - 當 `RequiredQty` 為負數時，邏輯可能不符合業務預期，因為所需數量不應為負。
  - 當查詢結果集為空時，無法確定庫存狀態，需確保在此情況下能正確返回 `False`。

- **風險**:
  - 如果資料庫查詢失敗或返回錯誤的結果，可能導致錯誤的庫存檢查結果。
  - 若未妥善處理資料類型轉換（如 `CInt`），可能會導致運行時錯誤。

## 建議測試案例
1. 測試 `StockQuantity` 大於 `RequiredQty` 時，應返回 `True`。
2. 測試 `StockQuantity` 等於 `RequiredQty` 時，應返回 `True`。
3. 測試 `StockQuantity` 小於 `RequiredQty` 時，應返回 `False`。
4. 測試 `StockQuantity` 為負數時，應返回 `False`。
5. 測試 `RequiredQty` 為負數時，應返回 `False`。
6. 測試查詢結果集為空時，應返回 `False`。
7. 測試 `StockQuantity` 為非整數（如字串或浮點數）時，應檢查是否能正確處理並返回 `False`。

# UpdateStock 決策邏輯

**來源**: `ProductForm.frm` / `UpdateStock`

## 業務規則說明
這個業務規則的目的是在更新庫存時，確保當用戶輸入的數量為負數（表示減少庫存）時，系統會檢查該產品的現有庫存是否足夠。如果庫存不足，則系統會引發一個錯誤，提示用戶庫存不足，無法完成該操作。

## 決策邏輯
- 當輸入的數量（Quantity）小於0時，進入檢查庫存的流程。
  - 使用 `CheckStock` 函數檢查指定產品（ProductID）是否有足夠的庫存來滿足減少的數量（取絕對值）。
  - 如果庫存不足（`CheckStock` 返回 False），則引發錯誤，提示「庫存不足」。

## 邊界條件與風險
- 當 `Quantity` 為負數時，必須確保 `CheckStock` 函數能正確計算庫存，否則可能導致錯誤的庫存狀態。
- 若 `ProductID` 無效或不存在，`CheckStock` 可能會返回錯誤，需確保該情況被妥善處理。
- 系統在高並發情況下可能會出現庫存檢查與更新的競爭條件，需考慮資料一致性問題。

## 建議測試案例
1. 測試當 `Quantity` 為負數且庫存足夠時，應該成功執行，不引發錯誤。
2. 測試當 `Quantity` 為負數且庫存不足時，應該引發「庫存不足」的錯誤。
3. 測試當 `Quantity` 為0時，系統應正常執行，不進行庫存檢查。
4. 測試當 `ProductID` 無效時，系統應該妥善處理並返回適當的錯誤訊息。
5. 測試在高並發情況下多個用戶同時嘗試減少庫存，確保系統能正確處理庫存狀態。

# 計算: sql

**來源**: `ProductForm.frm` / `UpdateStock`

## 業務規則說明
這條業務規則的目的是更新產品的庫存數量。當收到一個數量（Quantity）時，系統會將該數量加到目前的庫存數量（StockQuantity）上。這樣的操作通常用於補充庫存，確保產品的可用性。

## 決策邏輯
1. 當執行更新操作時，系統會生成一條 SQL 語句。
2. SQL 語句的格式為：`UPDATE Products SET StockQuantity = StockQuantity + [Quantity]`
3. 在這條語句中，`StockQuantity` 是目前的庫存數量，而 `Quantity` 是要新增的數量。
4. 最終，執行這條 SQL 語句將會更新資料庫中該產品的庫存數量。

## 邊界條件與風險
1. **負數的 Quantity**: 如果輸入的 Quantity 為負數，可能會導致庫存數量減少，需確認這是否符合業務邏輯。
2. **庫存數量為零**: 若庫存數量為零，更新後的庫存數量可能會變成負數，這可能不符合業務規範。
3. **資料庫連接問題**: 在執行 SQL 更新時，若資料庫無法連接，則更新將失敗。
4. **Concurrency Issues**: 若多個操作同時更新同一產品的庫存，可能會導致數據不一致。

## 建議測試案例
1. 測試正常情況：輸入一個正數的 Quantity，確認庫存數量正確更新。
2. 測試負數情況：輸入一個負數的 Quantity，確認系統是否正確處理（例如，是否允許或拒絕操作）。
3. 測試邊界情況：將庫存數量設定為零，然後輸入一個正數的 Quantity，確認庫存數量更新正確。
4. 測試資料庫連接失敗情況：模擬資料庫無法連接的情況，確認系統能正確處理錯誤。
5. 測試並發更新情況：同時執行多個更新操作，確認庫存數量的最終結果是否正確。

## 決策邏輯
1. 當 m_CustomerID = 0 時：
   - 執行 SQL 插入操作，將新客戶的資料（姓名、電子郵件、會員等級、創建日期、總購買金額）插入到 Customers 表中。
   
2. 當 m_CustomerID 不等於 0 時：
   - 執行 SQL 更新操作，根據 m_CustomerID 更新現有客戶的資料（姓名、電子郵件等）。

## 邊界條件與風險
1. **m_CustomerID 為負值**：如果 m_CustomerID 為負值，系統仍然會將其視為更新操作，這可能導致不正確的資料更新。

3. **資料完整性**：在執行插入或更新操作時，若某些必要欄位（如 CustomerName、Email 等）為空，可能會導致資料不完整或錯誤。
4. **日期格式問題**：若 m_CreateDate 的格式不正確，可能會導致資料庫插入失敗。

## 建議測試案例
1. 測試情境：m_CustomerID = 0，確認系統能正確執行插入操作並將所有必要資料正確插入資料庫。
2. 測試情境：m_CustomerID 不等於 0，確認系統能正確執行更新操作並更新相應的客戶資料。
3. 測試情境：m_CustomerID 為負值，確認系統行為是否符合預期（應該是更新操作）。
4. 測試情境：提供空值或不完整的客戶資料，確認系統能正確處理並返回相應的錯誤信息。
5. 測試情境：提供不正確格式的日期，確認系統能正確處理並返回相應的錯誤信息。
6. 測試情境：測試 SQL 注入攻擊，確認系統能抵禦此類攻擊並保持資料安全。

# CalculateDiscount 決策邏輯

**來源**: `Customer.cls` / `CalculateDiscount`

## 業務規則說明
這個業務規則的目的是根據客戶的會員等級和總消費金額計算折扣。具體來說，若客戶為VIP會員且其消費超過10,000元，則可享有15%的折扣；若僅為VIP會員，則享有10%的折扣；若消費超過5,000元，則可享有5%的折扣；在其他情況下，則不提供任何折扣。

## 決策邏輯
1. 如果客戶的會員等級為"VIP"且總消費金額超過10,000元，則折扣為15%。
2. 如果客戶的會員等級為"VIP"，但總消費金額不超過10,000元，則折扣為10%。
3. 如果客戶的總消費金額超過5,000元（但不是VIP會員），則折扣為5%。
4. 在所有其他情況下，折扣為0%。

## 邊界條件與風險
1. **會員等級的變化**：若會員等級變更（例如從VIP降級），可能會影響折扣計算。
2. **消費金額的邊界**：在邊界值附近（如5,000元和10,000元），需特別注意計算是否正確。
3. **數據完整性**：若客戶的消費數據不完整或錯誤，將影響折扣的計算結果。
4. **系統錯誤**：若系統出現錯誤，可能導致折扣計算不正確。

## 建議測試案例
1. 測試一名VIP會員，其總消費為12,000元，應獲得15%的折扣。
2. 測試一名VIP會員，其總消費為8,000元，應獲得10%的折扣。
3. 測試一名非VIP會員，其總消費為6,000元，應獲得5%的折扣。
4. 測試一名非VIP會員，其總消費為4,000元，應獲得0%的折扣。
5. 測試一名VIP會員，其總消費恰好為10,000元，應獲得10%的折扣。
6. 測試一名VIP會員，其總消費恰好為5,000元，應獲得0%的折扣。

# UpgradeMemberLevel 狀態邏輯 (m_TotalPurchase)

**來源**: `Customer.cls` / `UpgradeMemberLevel`

## 業務規則說明
這個規則的目的是根據客戶的總購買金額（m_TotalPurchase）來升級其會員等級（m_MemberLevel）。會員等級的提升不僅能夠鼓勵客戶增加消費，還能夠提升客戶的滿意度和忠誠度。根據不同的消費金額，客戶將被分配到不同的會員等級，從而享受相應的優惠和服務。

## 決策邏輯
1. 如果 m_TotalPurchase 大於或等於 50000，則 m_MemberLevel 設定為 "PLATINUM"。
2. 如果 m_TotalPurchase 大於或等於 20000，則 m_MemberLevel 設定為 "VIP"。
3. 如果 m_TotalPurchase 大於或等於 5000，則 m_MemberLevel 設定為 "GOLD"。
4. 如果以上條件均不符合，則 m_MemberLevel 設定為 "STANDARD"。

## 邊界條件與風險
1. **邊界條件**: 
   - 當 m_TotalPurchase 恰好等於 5000、20000 或 50000 時，應確保系統正確判斷並分配相應的會員等級。
   - 當 m_TotalPurchase 為負數或零時，系統應該能夠正確處理並將會員等級設為 "STANDARD"。

2. **風險**:
   - 若系統未能正確更新會員等級，可能會導致客戶對於會員制度的不滿。
   - 如果會員等級的變更未能及時反映在客戶的帳戶中，可能會影響客戶的購物體驗和忠誠度。

## 建議測試案例
1. 測試 m_TotalPurchase 為 50000，確認 m_MemberLevel 為 "PLATINUM"。
2. 測試 m_TotalPurchase 為 20000，確認 m_MemberLevel 為 "VIP"。
3. 測試 m_TotalPurchase 為 5000，確認 m_MemberLevel 為 "GOLD"。
4. 測試 m_TotalPurchase 為 4999，確認 m_MemberLevel 為 "STANDARD"。
5. 測試 m_TotalPurchase 為 0，確認 m_MemberLevel 為 "STANDARD"。
6. 測試 m_TotalPurchase 為負數（例如 -100），確認 m_MemberLevel 為 "STANDARD"。

# 計算: TotalAmount

**來源**: `OrderModule.bas` / `CreateOrder`

## 業務規則說明
此業務規則的目的是計算訂單的總金額（TotalAmount）。它通過將每個項目的數量（Quantity）與其單價（UnitPrice）相乘，然後將這些值累加到總金額中，來確保最終的訂單金額正確反映所有項目的價格。

## 決策邏輯
1. 循環遍歷所有項目（Items）。
2. 對於每個項目（Items(i)）：
   - 取得該項目的數量（Items(i).Quantity）。
   - 取得該項目的單價（Items(i).UnitPrice）。
   - 計算該項目的總價（Quantity * UnitPrice）。
   - 將該項目的總價加到總金額（TotalAmount）中。

## 邊界條件與風險
1. **項目數量為零**：如果某個項目的數量為零，則該項目的價格不應影響總金額。
2. **單價為零或負值**：若單價為零或負值，可能會導致計算錯誤或不合理的總金額。
3. **Items 陣列為空**：如果沒有項目，則總金額應保持為零。
4. **數據類型問題**：確保 Quantity 和 UnitPrice 的數據類型正確，避免因類型不匹配導致計算錯誤。

## 建議測試案例
1. 測試一個空的 Items 陣列，確認 TotalAmount 為零。
2. 測試一個只有一個項目的 Items 陣列，該項目的 Quantity 和 UnitPrice 均為正值，確認計算結果正確。
3. 測試一個項目的 Quantity 為零，確認該項目不影響 TotalAmount。
4. 測試一個項目的 UnitPrice 為零，確認該項目不影響 TotalAmount。
5. 測試一個項目的 UnitPrice 為負值，確認系統能正確處理此情況，並檢查 TotalAmount 是否合理。
6. 測試多個項目，確認 TotalAmount 的計算正確性。

# CalculateOrderTotal 決策邏輯

**來源**: `OrderModule.bas` / `CalculateOrderTotal`

## 業務規則說明
這項業務規則的目的是計算訂單的總金額（Subtotal）。根據資料庫中查詢結果的 "Subtotal" 欄位，若該欄位的值不為空（Not IsNull），則將其轉換為數字並賦值給 Subtotal；若該欄位為空，則將 Subtotal 設為 0。這樣的邏輯確保了在計算訂單金額時不會因為缺少數據而導致錯誤。

## 決策邏輯
- 如果 "Subtotal" 欄位的值不為空（Not IsNull(rs("Subtotal")）：
  - 將 "Subtotal" 欄位的值轉換為數字（CDbl）並賦值給 Subtotal。
- 否則（其他情況）：
  - 將 Subtotal 設為 0。

## 邊界條件與風險
- **邊界條件**：
  - 當 "Subtotal" 欄位的值為空（Null）時，系統應正確處理並返回 0。
  - 當 "Subtotal" 欄位的值為非數字型（例如字串或特殊字符）時，可能會導致轉換失敗，需考慮如何處理這種情況。
  
- **風險**：
  - 若資料庫查詢未正確執行，可能導致 Subtotal 無法正確計算。
  - 若未考慮到其他可能的數據類型或格式，可能會引發運行時錯誤。

## 建議測試案例
- 測試案例 1：當 "Subtotal" 欄位的值為有效的數字（例如 100.50），確認 Subtotal 是否正確設為 100.50。
- 測試案例 2：當 "Subtotal" 欄位的值為 Null，確認 Subtotal 是否正確設為 0。
- 測試案例 3：當 "Subtotal" 欄位的值為非數字型（例如 "abc"），確認系統是否能正確處理並返回預期的錯誤或預設值。
- 測試案例 4：當 "Subtotal" 欄位的值為負數（例如 -50），確認 Subtotal 是否正確設為該負數。

# CalculateOrderTotal 決策邏輯

**來源**: `OrderModule.bas` / `CalculateOrderTotal`

## 業務規則說明
這個業務規則的目的是計算訂單的折扣率。根據會員的等級和總購買金額，系統會決定是否應用折扣。如果會員資料存在（即資料集未到達結尾），則根據會員等級和總購買金額來獲取相應的折扣率；如果會員資料不存在，則不提供任何折扣，折扣率設為0。

## 決策邏輯
1. 檢查資料集是否未到達結尾（Not rs.EOF）。
   - 如果是，則：
     - 使用會員等級和總購買金額調用 `GetDiscountRate` 函數來計算折扣率。
   - 如果不是，則：
     - 折扣率設為0。

## 邊界條件與風險
1. **資料集為空**：如果資料集為空，則永遠會返回折扣率0，可能導致無法正確計算折扣。
2. **會員等級或總購買金額無效**：如果 `GetDiscountRate` 函數無法處理某些會員等級或總購買金額，可能會導致錯誤或異常。
3. **資料型別問題**：在將資料轉換為字串或雙精度浮點數時，若資料格式不正確，可能會引發運行時錯誤。
4. **邊界值**：會員等級和總購買金額的邊界值（例如，剛好達到折扣的門檻）可能會導致不同的折扣率。

## 建議測試案例
1. **正常情況**：提供有效的會員等級和總購買金額，確認能正確計算折扣率。
2. **資料集為空**：測試資料集為空的情況，確認折扣率為0。
3. **無效會員等級**：提供無效的會員等級，確認系統能妥善處理並返回預期結果（例如，折扣率為0或錯誤處理）。
4. **邊界值測試**：測試會員等級和總購買金額在折扣門檻附近的情況，確認系統能正確計算折扣率。
5. **資料型別測試**：測試傳入非數字或非字串的資料，確認系統的穩定性和錯誤處理能力。

# 計算: sql

**來源**: `OrderModule.bas` / `CalculateOrderTotal`

## 業務規則說明
這條業務規則的目的是計算訂單的總金額（Subtotal），該金額是通過將每個商品的數量（Quantity）與其單價（UnitPrice）相乘後，對所有商品的結果進行求和來獲得的。這個計算是用於訂單模組中，以便在顯示或處理訂單時能夠提供正確的金額資訊。

## 決策邏輯
1. 從資料庫中選取所有訂單項目的數量（Quantity）和單價（UnitPrice）。
2. 對每個訂單項目計算其小計（Quantity * UnitPrice）。
3. 對所有訂單項目的小計進行求和，得到最終的訂單總金額（Subtotal）。

## 邊界條件與風險
1. **數據完整性**: 若資料庫中有缺失的數量或單價資料，可能導致計算結果不正確。
2. **數據類型**: 確保Quantity和UnitPrice的數據類型正確，若有非數字型別的資料進入計算，將會導致錯誤。
3. **性能問題**: 當訂單數量非常龐大時，計算可能會影響性能，需考慮優化查詢。
4. **邊界條件**: 當Quantity為0或UnitPrice為0時，計算結果應正確處理，避免出現不合理的Subtotal。

## 建議測試案例
1. 測試一個正常的訂單，包含多個商品，確保Subtotal計算正確。
2. 測試一個訂單，其中一個商品的Quantity為0，確認Subtotal仍然正確。
3. 測試一個訂單，其中一個商品的UnitPrice為0，確認Subtotal仍然正確。
4. 測試一個訂單，包含數量和單價為負數的商品，確認系統能正確處理並返回合理的Subtotal。
5. 測試一個空訂單（無商品），確認Subtotal為0。

# 計算: Tax

**來源**: `OrderModule.bas` / `CalculateOrderTotal`

## 業務規則說明
這個業務規則的目的是計算訂單的稅金。根據訂單的總金額（Subtotal）和適用的稅率（TAX_RATE），計算出應收的稅金（Tax）。這是訂單處理過程中的一個關鍵步驟，確保最終金額的準確性，並符合相關的稅務法規。

## 決策邏輯
1. 接收輸入變數：Subtotal（訂單總金額）和TAX_RATE（稅率）。
2. 使用公式計算稅金：Tax = Subtotal * TAX_RATE。
3. 返回計算出的稅金（Tax）。

## 邊界條件與風險
1. **TAX_RATE的有效性**：需要確認TAX_RATE的值是否在合理範圍內（例如，不能為負數或過高的百分比）。
2. **Subtotal的有效性**：Subtotal應為非負數，若為負數則可能導致稅金計算錯誤。
3. **四捨五入問題**：計算結果可能需要進行四捨五入，特別是在顯示給客戶時，需確保稅金的顯示精度符合商業慣例。
4. **稅率變更**：需考慮稅率可能會隨時間或地區變更，系統需具備靈活調整稅率的能力。

## 建議測試案例
1. 測試正常情況：使用正確的Subtotal和TAX_RATE，確認計算結果正確。
2. 測試TAX_RATE為0的情況：確認稅金計算結果為0。
3. 測試Subtotal為0的情況：確認稅金計算結果為0。
4. 測試TAX_RATE為負數的情況：確認系統能正確處理並返回錯誤或異常。
5. 測試TAX_RATE為非常高的情況：確認系統能正確處理並返回錯誤或異常。
6. 測試Subtotal為負數的情況：確認系統能正確處理並返回錯誤或異常。
7. 測試計算結果的四捨五入：確認稅金在顯示時符合商業慣例的精度要求。

# 計算: 最終金額

**來源**: `OrderModule.bas` / `CalculateOrderTotal`

## 業務規則說明
這個業務規則的目的是計算訂單的最終金額。最終金額是根據訂單的小計、折扣和稅金進行計算的。具體來說，最終金額是從小計中減去折扣，然後再加上稅金，這樣可以確保客戶在結帳時能夠看到正確的金額。

## 決策邏輯
- **計算最終金額的公式**:
  1. 從小計中減去折扣。
  2. 將結果加上稅金。
  3. 得到的結果即為最終金額。

## 邊界條件與風險
- **邊界條件**:
  1. 小計、折扣和稅金的數值必須為數字型態，且不得為負數。
  2. 折扣的數值不能超過小計的數值，否則會導致最終金額為負。
  3. 稅金的計算基礎必須明確，若稅金計算方式變更，則需重新評估最終金額的計算。

- **風險**:
  1. 如果折扣或稅金的計算邏輯有誤，將直接影響最終金額的準確性。
  2. 使用者輸入錯誤的數值（例如負數或非數字）可能導致計算錯誤或系統崩潰。
  3. 系統未考慮到不同地區的稅率差異，可能導致稅金計算不正確。

## 建議測試案例
1. 測試小計為正數，折扣為正數且小於小計，稅金為正數，確保最終金額正確計算。
2. 測試小計為正數，折扣為0，稅金為正數，確保最終金額等於小計加稅金。
3. 測試小計為正數，折扣等於小計，稅金為0，確保最終金額為0。
4. 測試小計為正數，折扣為負數，稅金為正數，確保系統能正確處理此情況（應該拒絕負數折扣）。
5. 測試小計為0，折扣為0，稅金為0，確保最終金額為0。
6. 測試小計為正數，折扣為正數且大於小計，稅金為0，確保最終金額不為負數。
7. 測試不同稅率的情況，確保稅金計算正確。

# 計算: CalculateOrderTotal

**來源**: `OrderModule.bas` / `CalculateOrderTotal`

## 業務規則說明
這個業務規則的目的是計算訂單的總金額。它考慮了訂單的基本金額（Subtotal）、折扣率（DiscountRate）以及稅金（Tax）。最終計算的結果將用於確定客戶需要支付的金額。

## 決策邏輯
1. 計算折扣後的金額：
   - 使用公式 `Subtotal * (1 - DiscountRate)` 計算折扣後的金額。
2. 加上稅金：
   - 將折扣後的金額與稅金相加，得到最終的訂單總金額。
3. 返回計算結果：
   - 將計算出的總金額作為結果返回。

## 邊界條件與風險
1. **折扣率的範圍**：
   - 如果折扣率（DiscountRate）超過1或小於0，可能會導致計算結果不正確。
2. **稅金的計算**：
   - 稅金（Tax）是否正確計算，特別是在不同地區稅率不同的情況下。
3. **Subtotal的有效性**：
   - Subtotal必須為非負數，否則計算結果將不合理。
4. **浮點數精度問題**：
   - 在計算過程中可能會出現浮點數精度的問題，特別是在涉及金額計算時。

## 建議測試案例
1. **正常情況**：
   - 測試一個正常的訂單，Subtotal = 100，DiscountRate = 0.1，Tax = 5，預期結果為95。
2. **無折扣情況**：
   - 測試Subtotal = 100，DiscountRate = 0，Tax = 5，預期結果為105。
3. **全額折扣情況**：
   - 測試Subtotal = 100，DiscountRate = 1，Tax = 5，預期結果為5。
4. **負數Subtotal情況**：
   - 測試Subtotal = -50，DiscountRate = 0.1，Tax = 5，預期結果應該拋出錯誤或返回不合理的結果。
5. **極端折扣情況**：
   - 測試Subtotal = 100，DiscountRate = 1.5，Tax = 5，預期結果應該拋出錯誤或返回不合理的結果。
6. **稅金為負數情況**：
   - 測試Subtotal = 100，DiscountRate = 0.1，Tax = -5，預期結果應該拋出錯誤或返回不合理的結果。

# GetDiscountRate 決策邏輯

**來源**: `OrderModule.bas` / `GetDiscountRate`

## 業務規則說明
這個業務規則的目的是根據顧客的總購買金額來決定折扣率。當顧客的總購買金額超過 10,000 時，將給予較高的折扣率 15%。如果總購買金額不超過 10,000，則適用較低的折扣率 10%。這樣的設計旨在鼓勵顧客進行更高金額的購買，以獲得更優惠的折扣。

## 決策邏輯
- 如果總購買金額（TotalPurchase）大於 10,000：
  - 折扣率（GetDiscountRate）為 15%。
- 否則：
  - 折扣率（GetDiscountRate）為 10%。

## 邊界條件與風險
- **邊界條件**：
  - 總購買金額恰好為 10,000 的情況，需確認系統是否正確處理此邊界值。
- **風險**：
  - 如果系統未能正確計算或更新折扣率，可能會導致顧客不滿意，影響銷售和顧客忠誠度。
  - 需要確保在不同的貨幣或稅務情況下，折扣計算仍然正確。

## 建議測試案例
1. 測試總購買金額為 10,001，確認折扣率為 15%。
2. 測試總購買金額為 10,000，確認折扣率為 10%。
3. 測試總購買金額為 9,999，確認折扣率為 10%。
4. 測試極端情況，如總購買金額為 0，確認折扣率為 10%。
5. 測試系統在不同貨幣下的折扣計算是否正確。

# GetDiscountRate 狀態邏輯 (MemberLevel)

**來源**: `OrderModule.bas` / `GetDiscountRate`

## 業務規則說明
這個業務規則的目的是根據會員等級（MemberLevel）來決定折扣率（GetDiscountRate）。不同的會員等級對應不同的折扣率，這樣可以激勵顧客升級會員等級以獲得更高的折扣。此規則主要用於訂單模組中，以便在結帳時計算適用的折扣。

## 決策邏輯
1. 如果會員等級為 "PLATINUM"，則折扣率為 20%（0.2）。
2. 如果會員等級為 "VIP"，則：
   - 若總購買金額（TotalPurchase）大於 10,000，則折扣率為 15%（0.15）。
   - 否則，折扣率為 10%（0.1）。
3. 如果會員等級為 "GOLD"，則折扣率為 5%（0.05）。
4. 如果會員等級為其他（Else），則折扣率為 0%。

## 邊界條件與風險
1. **會員等級的正確性**：需確保會員等級的資料正確無誤，若等級錯誤將導致錯誤的折扣計算。
2. **總購買金額的計算**：在 "VIP" 等級中，折扣率依賴於總購買金額的正確計算，若計算錯誤將影響折扣的正確性。
3. **邊界值測試**：對於總購買金額在 10,000 附近的情況（如 9,999 和 10,000）需特別注意，以確保折扣計算的正確性。
4. **會員等級變更的即時性**：若會員等級在購物過程中變更，需確保折扣計算能即時反映最新的會員等級。

## 建議測試案例
1. 測試會員等級為 "PLATINUM" 時，確認折扣率為 0.2。
2. 測試會員等級為 "VIP" 且總購買金額為 10,000 時，確認折扣率為 0.15。
3. 測試會員等級為 "VIP" 且總購買金額為 9,999 時，確認折扣率為 0.1。
4. 測試會員等級為 "GOLD" 時，確認折扣率為 0.05。
5. 測試會員等級為其他（如 "SILVER"）時，確認折扣率為 0。
6. 測試會員等級在購物過程中變更的情境，確認折扣計算能即時反映最新的會員等級。
